# rpart：ピタゴラスの相手の列挙による全平面の箱探索

2026年11月5日、mathematics-52。手法の元は GitHub の Mulatram-UwU/rational-distance-problem（内部だけ、共通分母 5×10¹⁰）。
当方はコードを使っていない。手法を読んで、符号つきの全平面の箱に広げて Rust で書き直した。

## 覆う範囲

点を (A/Q, C/Q)（Q ≥ 1、A・C は符号つき整数）、B = Q−A、D = Q−C とする。
4 頂点への距離がすべて有理数であることは、A²+C²・B²+C²・A²+D²・B²+D² がすべて平方数であることと同じである。

rpart は、Q ≤ N かつ max(|A|, |B|, |C|, |D|) ≤ M のすべての (Q, A, C) を調べる。
M = K·N とすると、箱 [1−K, K]² の中の、共通分母 ≤ N のすべての点を覆う。

## 列挙

a = |A|、b = |B|、c = |C|、d = |D| とおく。T(c) = {v ≥ 1 : c²+v² は平方数} とする。

1. c を 1 から M まで回す。T(c) ∩ [1, M] を c² の約数から作る（u·w = c²、u < w、u ≡ w (mod 2)、v = (w−u)/2）。
2. T(c) の中の組 a < b ごとに、Q = a+b（0 < x < 1）と Q = b−a（x が [0,1] の外）を試す。
3. Q ごとに d = |Q−c| と d = Q+c を試し、a²+d² と b²+d² を平方判定する。

境目の場合は次のように覆う。

- a = 0 や b = 0（直線 x = 0, 1 の上）は、対称 (x,y) ↔ (y,x) と d = 0 の場合で覆う。
- a = b は x = 1/2 のときだけ起こる。同じ対称で覆うが、中心 (1/2, 1/2) だけは覆わない。中心の距離は √2/2 で無理数なので、解にならない。

## 絞り込み

最小の分母をとると gcd(A,B,C,D) = 1 になる。このとき mod 8 と mod 3 の補題から、次が成り立つ。

- c ≡ 2 (mod 4) は起こらない。
- c が奇数なら a ≡ b ≡ 0 (mod 4) である。
- 4 | c なら a・b は奇数である。
- 3 | a と 3 | b は同値である。
- 12 | Q である。

`check/residue_check.py` で、偶数でない剰余の組を mod 48 と mod 144 で全部調べ、違反は 0 件だった。
組の数 1,280 と 34,560 は、元の報告の表と一致する。

## 試して採らなかった高速化（v2/、11/05）

## 平方判定を速めた版（v3/、11/05、本走に採用）

1 スレッドで c ≤ 10⁶（N = 10¹⁰、M = 10¹¹）を測ると、時間の約 87% が a²+d²・b²+d² の平方判定だった。
v3 は平方判定だけを次の形に替えた。列挙・絞り込み・出力は v1 と同じ。

1. 下位 64 ビットの mod 64 で平方剰余でないものを落とす。
2. f64 で √(a²+d²) を求めて丸める（M ≤ 2⁴⁰ なので誤差は 2⁻¹⁰ 未満）。
3. u128 で r² = a²+d² を正確に確かめる。

## 約数の木と因数分解を軽くした版（v4/、11/05 夕、P4 に採用）

v3 を `sample` で測ると、軽い区間（c ≈ 5×10¹¹、M = 10¹²）では約数の木（`partners`）が約 42%、組の回し方が約 42%、平方判定が約 11%、因数分解が約 3% だった。v4 は次の 3 つを替えた。列挙する相手・組・候補・3 距離の行は v3 と同じで、約数の木の節の数（`divisor_nodes`）だけが減る。

1. 約数の木を u128 から u64 に替えた。積は飽和させる。訪れる節では u < c ≤ 2⁴⁰、w ≤ 2M + c < 2⁴² なので、飽和した値は必ず上限を超えるか c 以上になり、v3 と同じ所で切られる。
2. 4 | c のとき、残すのは v が奇数の相手だけなので、u の 2 の指数を 1 と 2e−1（2e は c² の 2 の指数）だけに絞った。v = (w−u)/2 が奇数になるのは u・w の片方だけが 2 (mod 4) のときなので、捨てる葉だけを先に刈る。内部の件数を数えるとき（`--interior-stats`）は刈らない。
3. 因数分解の割り算を、奇素数の 2⁶⁴ を法とする逆元による割り切れ判定（x·p⁻¹ ≤ ⌊(2⁶⁴−1)/p⌋）に、2 は末尾の 0 の数に替えた。素因数の並べ替えは逆順にするだけにした（小さい順に並び、残りの素数が最大）。

| 照合 | 結果 |
|---|---|
| 総当たり 5 箱（絞り込みあり・なし） | すべて完全一致 |
| 内部の件数（N = 10⁴〜10⁷） | 4 つとも完全一致 |
| v3 との全カウンタ（`divisor_nodes` を除く）と 3 距離の行：(10⁶, 10⁷)、(10⁸, 10⁹) の c ≤ 10⁶、N10¹⁰/M10¹¹ の c ≤ 3×10⁵ と c ≈ 5×10¹⁰、N10¹¹/M10¹² の c ≤ 2×10⁵・c ≈ 2³⁹・M の直前 3×10⁵ | すべて完全一致 |
| v3 の出力先を飛ばして v4 で残りを回し、まとめた結果（(10⁶, 10⁷)、5 区間） | 一括実行と一致 |

軽い区間 1 スレッドで v3 2.86 秒 → v4 2.48 秒（約 1.15 倍）。c の小さい重い区間ではほぼ同じ。
組の判定を mod 12 の表引きに替える案も試したが、遅くなった（2.48 → 2.62 秒）ので入れていない。

オーバーフローの確認：M ≤ 2⁴⁰（起動時に assert）。平方は u128 で正確、f64 の平方根の誤差は 2⁻¹⁰ 未満、a+b ≤ 2M・Q+c ≤ N+M・2M+c は u64 に収まる。

## 平方判定の無駄なふるいを外した版（v5/、11/06 朝、P4 の M1・Intel の残りに採用）

c の小さい区間（c ≈ 10⁸、M = 10¹²）では、組の 73% が Q の候補になり、時間の大半は a²+d²・b²+d² の平方判定だった。
v3・v4 は平方判定の前に mod 64 で平方剰余でないものを落としていたが、絞り込みありの探索ではこのふるいは何も落とさない。
a・d の片方が 4 の倍数で他方が奇数なので a²+d² ≡ 1 (mod 8) になり、8 で割って 1 余る奇数は mod 64 ですべて平方剰余だからである。

v5 は v4 から平方判定だけを次のように替えた。列挙・絞り込み・出力・全カウンタ（`divisor_nodes` も）は v4 と同じ。

1. mod 64 のふるいを外した。
2. 最後の確かめを u128 から u64 の wrapping 演算に替えた。r = round(√(a²+d²)) のとき |r² − (a²+d²)| ≤ 2r+1 < 2⁴³ なので、2⁶⁴ を法として等しければ本当に等しい。

| 照合 | 結果 |
|---|---|
| 総当たり 5 箱（絞り込みあり・なし） | すべて完全一致 |
| 内部の件数（N = 10⁴〜10⁷、`--all --interior-stats`） | 4 つとも v4・元の公表値と完全一致 |
| v4 との全カウンタ（`divisor_nodes` を含む）と 3 距離の行：(10⁶, 10⁷)、(10⁸, 10⁹) の c ≤ 10⁶、N10¹⁰/M10¹¹ の c ≤ 3×10⁵ と c ≈ 5×10¹⁰、N10¹¹/M10¹² の c ≤ 2×10⁵・c ≈ 2³⁹・M の直前 3×10⁵ | すべて完全一致 |
| v4 の出力先を飛ばして v5 で残りを回し、まとめた結果（(10⁶, 10⁷)、5 区間） | 一括実行と一致 |

試して採らなかった案（どれも結果は v4 と一致したが遅かった）：

- 奇数の法 45045 = 9·5·7·11·13 の平方剰余の表でふるう：1.56 → 4.2 秒。通るかどうかがでたらめな分岐になり、予測が外れる損が浮動小数の平方根より大きい。
- f64 だけで「√x が整数から 2⁻¹⁰ 以内か」を先に見る：1.31 秒。
- 相手ごとに a² を前もって作る：1.20 秒で、v5 と変わらない。
- 組の中身を分岐なしにして無効な所は捨てる：1.47 秒。
